# WI-EXC verification: independent adversarial review

Verifier's report on work item WI-EXC (spec exceptions-intc). The units under test are `rtl/v1/v1_intc.sv` and
`rtl/v1/v1_excregs.sv`, the C++ model `tb/sh4_intc.h`, the unit tb `tb/v1_intc_tb.{sv,cpp}` (with `tb/mk/v1_intc.mk`,
`tb/v1_intc_mutants.py`, `tb/v1_intc_lint.vlt`) and the bare-metal ports in `tb/bm/exceptions-intc/`. No repo file was
edited. All new tests, logs and builds are under `agents/verify/WI-EXC/` and `agents/scratch/WI-EXC/`.

## Verdict

The implementation is sound and matches the contract. Both port lists are exactly those in SOC.md §3.8. Every register,
mask, reset value, size rule, the resolver order, the IRL and NMI decision times, and the IMASK structure are
correct. The implementer's results all reproduce. My adversarial coverage (group C, 7 checks) passes. A mutation run of
those checks catches 8 of 8 planted bugs, so the checks can fail.

The findings below are:
- one manual deviation: MAI in standby;
- one weak M1a gate that hides a 4-7 cycle calibration gap in the IPR-write → interrupt path;
- one non-reproducible calibration input;
- several minor or [P]-unmarked choices.

None of them breaks the DC boot path: the NMI is tied high, IRLM = 0, and nothing on the DC writes the exception
registers over DMA.

## Findings (most severe first)

### 1. [weak-test] The IPR / UNIE write → interrupt path is 4-7 Icyc fast end to end, and expected.json accepts it

- **Where:** `tb/bm/exceptions-intc/expected.json`, entries "C1 ipr_write", "C1 unie_write" and "S PI ipra". The cause
  is `v1_intc.sv`'s IPR path (6 Icyc from the strobe, [P]) combined with `v1_p4bus`'s posted-write strobe point.
- **Repro:** `agents/verify/WI-EXC/run.sh` runs `p4intc` (the E1 line).
  - The CPU master presents the IPRA store (0xFFD00004 ← 0x0F00, TMU1 pending, IMASK 6) at MA1 = x, at every phase.
  - The bridge acks at x+2 and strobes the INTC at x+3 to x+6.
  - irq.req rises at **x+9 to x+12**.
  - In v1's schedule of `t_chain_st16` (the store pairs with `mov #0`; mah in MA1 and MA2; add_i at x+1+i), that is
    k = **8 to 11**.
  - The console measured **13 / 17 / 15 ×6** (warm 15).
- **Problem:** the `C1 ipr_write` and `unie_write` regexes accept k = 8-21 per trial (`[89]|1\d|2[01]`), and PI accepts
  8-24. So the M1a gate passes the SoC even though it is 4-7 cycles faster than every console trial.
  - Unlike the other widened lines, these have no cache argument: the console value is warm and steady.
  - TCR.UNIE (TMU level → INTC 4 / 5) and IPRA (INTC 6) give the same console k. So the missing cycles are common to
    both paths: the bridge's posted-write strobe point (it strobes at the first pce after MA3, not at the end of the
    2-Pcyc drain) or the core's store schedule, not the INTC alone.
- **Fix:**
  - Pin both C1 lines to the console set {13, 15, 17}, widened by at most the model's documented phase spread.
  - Make the IPR / UNIE write → request number an explicit M1a calibration item shared by WI-P4 and WI-EXC (SOC §9.4 /
    §9.13).
  - The implementer's open question says the same thing, but the gate should fail until it is settled.

### 2. [bug] MAI = 1 in standby: an NMI edge is still latched and ends standby once the pin is high again

- **Where:** `v1_intc.sv` lines 133-150 (the edge detector does not look at MAI in standby) and line 298 (`wake_stby`);
  also `tb/sh4_intc.h` `set_nmi_pin` / `wake_stby`.
- **Manual:** hm 19.4.3 (hm.txt 27231-27236) says: *"In standby mode: All interrupts are masked while the NMI pin is low,
  and an NMI interrupt is not generated by a transition at the NMI pin. Therefore, standby cannot be cleared by an NMI
  interrupt while the MAI bit is set to 1."* The note to the MAI bit description (hm.txt 27081-27083) says the same.
- **Repro:** `agents/scratch/WI-EXC/obj_adv/adv --only A`.
  - **A1:** MAI = 1, standby, pin 1 → 0 → 1. `wake_stby` is 0 while the pin is low but becomes **1** when the pin
    returns high. This happens with NMIE = 0 (the latched falling edge) and with NMIE = 1 (the rising edge).
  - **A3:** the same edge, then standby is ended by ATI. After `stby` falls the INTC presents **nmi = 1, code 0x1C0**
    instead of ATI's 0x480, so a spurious NMI is taken. `nmi_evt` pulsed once in standby (DMAOR.NMIF).
- **Fix:** in standby with `icr_mai`, gate `nmi_edge` (and `nmi_evt`) so that no NMI is latched. This also removes the
  need for the `!mai_mask` term on `nmi_pend` in `wake_stby`. Make the same change in `Sh4Intc`.
- **Impact:** none on the DC (the NMI is tied high). It is a manual deviation in a "complete SH7091".

### 3. [missing] The calibration tables of the `progs` group cannot be reproduced

- **Where:** `tb/v1_intc_tb.cpp`, lines 440-567 (the boundary offsets of ci2, excint C1, excint3 and the PH sweep).
- **Problem:** these offsets are the evidence for SOC §9.4, the "one structure" claim. They came from a trace harness
  that ran `v1_core.sv` on each program's code. That harness lived in the lost session scratchpad (resume_done.json:
  "a scratch harness in the session scratchpad (not in the repo)"). Nothing under `agents/scratch/` or `build/`
  contains it.
  - The tb itself says the tables "must be re-derived if WI-CORE-A changes the LDC SR, RTE or refetch schedule".
  - WI-CORE-A is editing `v1_core.sv` now (modified 08:19 today).
- **Repro:** `ls agents/scratch/` (WI-EXC contains only this verifier's files) and search the repo for a v1 trace driver
  of `t_chain_*` or `t_ph*`: there is none.
- **Fix:** re-create the trace driver as a repo tool, e.g. a `make v1-intc-sched` target that re-derives the tables
  from the current core and diffs them against `v1_intc_tb.cpp`. Until then the §3.4 fit is only as good as the
  frozen tables.

### 4. [minor / contract] `irq.code` changes while `irq.req` stays 1

- **Where:** `v1_intc.sv` lines 237-239 and 293. The contract is the `irq_t.code` comment in `v1_soc_pkg.sv`: "its
  INTEVT, stable while req".
- **Repro:** `adv --only B1`.
  - TMU1 at level 10 is requesting (code 0x420).
  - WDT ITI rises at level 12: the code becomes **0x560** with req held at 1 throughout.
  - When ITI drops the code goes back to 0x420, again with req held (B2).
- **Assessment:** the behaviour is right for a priority INTC (INTEVT is the winner at acceptance, hm 19.4.1). The core
  latches the code at the take (SOC §4.3.4 step 1), so nothing breaks. The package wording is wrong or ambiguous.
- **Fix:** the lead should reword it as "valid while req; sampled by the core at the take". Do not add holding logic.

### 5. [missing] The IMASK-raise direction is an unmarked [P] with cross-unit consequences

- **Where:** `v1_intc.sv` lines 221-241 (the same synchroniser in both directions). SOC §3.4 specifies only IMASK
  *falling*; the implementer's tb enforces 9 / 10 for the raise too (`imask`, "6->15 (masking)").
- **Repro:** `adv --only D1`.
  - TMU1 at level 10 rises at s-2 with IMASK 6, and IMASK is raised to 15 at s (KOS `irq_disable`).
  - irq.req is **1 from s+2/3 to s+8/9**.
  - The core would therefore accept a level-10 interrupt with SR.IMASK = 15 at the refetched instruction.
- **Consequences:**
  - It was never measured on the console.
  - SOC §6.2's lockstep legality check ("level vs IMASK from its own IPR / IRL copy") will flag such entries.
  - KOS critical sections become interruptible for up to about 8 cycles.
- **Fix:** mark it [P] in the RTL header and report it as a contract issue. The lead then either records a legality
  window of s + 10 for WI-REF, or specifies an immediate raise path (IMASK compare bypass on raise), whichever the
  console agrees with. A PH-style probe could measure it, with a source rising just before `irq_disable`.

### 6. [minor] `v1_excregs`: a bus write in the same cycle as `excw` is dropped, even for a different register

- **Where:** `v1_excregs.sv` lines 74-82 (`else if (wr32)`). The comment at lines 19-20 argues a collision cannot
  happen, but that ignores the DMAC master: an on-chip leg to 0x1F000020-28 decodes to CCN_EXC (SOC §3.1.1) and can
  strobe in any cycle.
- **Repro:** `adv --only B4`.
  - excw (EXPEVT ← 0x0E0) and a DMAC write TRA ← 0x3FC in one cycle: TRA reads **0x000**.
  - excw (INTEVT ← 0x420) with a DMAC write EXPEVT ← 0x555: EXPEVT reads 0x0E0.
  - The slave acked both writes.
- **Fix:** apply priority per register: a bus write lands unless `excw` writes that same register this cycle.

### 7. [weak-test, minor] The M1a gate barely checks "INTEVT is kept across general exceptions" [HW]

- **Where:** expected.json. 73 records print `EXP= INT=`; only 4 pin INT, and 3 of those are board-only (M4). The rest
  use `INT=[0-9a-f]{3}`.
- **Repro:** `python3 tb/bm/exceptions-intc/check.py agents/verify/WI-EXC/synthetic_intevt_bug.txt`.
  - The input is the console log with the SoC stub lines and INT set equal to EXP in every record, i.e. a core whose
    `excw.intr` also writes INTEVT on exceptions.
  - excint reports **1 failure** (`prio_irq_ill`); the other 59 corrupted records pass.
  - A core that misroutes only some classes (e.g. TRAPA or data faults) would pass.
- **Fix:** on the SoC INTEVT is 000 after the POR until the first interrupt probe. Pin `INT=000` for the records
  before C1, or add a relation "INT equals the previous record's INT" for general-exception records.

### 8. [minor] IRLM = 1: one 4-bit noise canceller couples the four "independent" requests (unmarked [P])

- **Where:** `v1_intc.sv` lines 157-167.
- **Repro:** `adv --only B3`.
  - IRLM = 1, IRL0 held low (level 13 > IMASK 12), and IRL3 toggling every 2 Bcyc.
  - IRL0 is **never** recognised in 400 Icyc, because the vector never has 3 equal samples.
- **Assessment:** hm 19.2.2 describes the canceller on "the levels", which fits IRLM = 0. With IRLM = 1, Table 19.4
  calls the pins independent requests. The DC uses IRLM = 0.
- **Fix:** mark it [P] (or filter per pin when IRLM = 1).

### 9. [minor] Unmarked [P]: an NMIB write in the `nmi_ack` cycle

- **Repro:** `adv --only C8`. An ICR write of NMIB = 1 in the same cycle as `nmi_ack` leaves NMIB = 0: acceptance wins.
- **Fix:** add a [P] comment next to `v1_intc.sv` line 276.

### 10. [cross-unit note] `wake` never changes "right after a pce"

- **Repro:** `adv --only D2`. `wake` (= `rq`) becomes visible in ph-1 or ph-3 cycles, 4 or 5 Icyc after the source.
- **Problem:** `v1_cpg.sv` lines 37-40 derive the 8-Icyc RESYNC from "the INTC's wake changing right after a pce". With
  the real INTC, RESYNC is 6 or 8 by phase.
- **Owner:** this is WI-CLK's assumption, not a WI-EXC defect. It matters for the M1a SLEEP wake cost (8-12 [HW]).

## Checked and correct (adversarial coverage, all PASS)

- **Ports:** `v1_intc` and `v1_excregs` are exactly SOC §3.8, in names, order and types. `irq_ack` is unused, with a
  waiver and a stated reason.
- **Registers, masks and holes:**
  - ICR reads 0x8000 or 0x0000 by the pin; after writing 0xFFFF it reads 0xC381 (bit 0 storage, NMIL read-only).
  - IPRA / IPRC take 0xFFFF and IPRB takes 0xFFF0; IPRD (0x10) is a hole.
  - Every offset 0x00-0x3F at all three sizes follows the size rule and the holes (C7).
  - TRA 0x3FC, EXPEVT / INTEVT 0xFFF, and the 256-byte CCN repeat.
- **Resets:**
  - POR clears TRA / INTEVT; manual and CPU-only resets hold them.
  - EXPEVT is 000 / 020 / 140 per `rst_code`.
  - Across 20,000 random excregs operations (bus writes of all sizes, excw, every reset kind) there were 0 mismatches
    (C5).
  - A CPU-only reset holds the NMI latch and the IRL filter; a manual reset clears both (C2).
- **Resolver and IRL:**
  - Every IRL pin value × IRLM 0 / 1 × IMASK 0-15 matches hm Tables 19.3 / 19.4 / 19.5, checked independently of
    `sh4_intc.h` (C1).
  - The on-chip fields and order match hm Table 19.5 (checked by hand against hm.txt 26860-26990).
- **IMASK timing:** every (from, to) pair × 4 phases gives s+9 (even s) / s+10 (odd s), with no glitch when the
  comparison does not change (C4).
- **NMI:** BL, NMIB, sleep and MAI, all 16 combinations; `wake` is 1 with an NMI pending (C3).
- **Standby IRL:** wakes after 5 `rtc_tick` samples; a 2-tick glitch does not wake (C6).
- **Blind window:** re-derived; it is exactly 6 bce detector cycles.
- **PH sweep:** the implementer's I-cache explanation of the console's 0 and 6 values is self-consistent. Every 6 falls
  on the first add of a new 32-byte line, and every 0 has the line 1-4 adds away. The bm layout keeps those positions
  (mod 32 bytes). Final confirmation belongs to M3 (WI-CACHE / WI-CORE-B), because M1a runs with IDEAL_MEM.

## Contract issues for the lead

1. `irq_t.code` "stable while req" (pkg) should read "valid while req; the core latches it at the take" (finding 4).
2. SOC §3.4 specifies only the IMASK-lowering latency. The raising direction needs a decision, and WI-REF's legality
   check needs the resulting window (finding 5).
3. The absolute IPR / UNIE write → request time is a WI-P4 + WI-EXC calibration. Record it next to §9.4 / §9.13, and
   keep the expected.json gate at the console values (finding 1).
4. I agree with the implementer's proposed §3.4 wording: "irq.req rises at s + 9 when s is even, s + 10 when s is odd".
   I also agree that the PH / P_D2 parity coupling should be recorded with §9.13.
5. For WI-CLK: the RESYNC phase assumption about `wake` (finding 10).

## Open questions

- Whether the silicon masks immediately when IMASK rises (finding 5). This can be measured safely with a PH-style
  sweep: a TMU source rising just before `irq_disable`.
- The C1 / PI gap (finding 1): is the write landing at the end of the Pclk drain (WI-P4), or is the core's store
  schedule different? M1a should decide with the gate tightened.
