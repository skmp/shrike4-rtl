## 2. The dcload-ip stand-in (`tools/boot/stub/dcload.S`; board option `--dcload`; SOC.md 7.2, board.md 5.2)

**Why it is needed.** Every console probe ran under dcload-ip 2.0.3, and KOS behaves differently when dcload is there.
- It finds 0xDEADBEEF at 0x8C004004, and its dbgio console is dcload's write syscall, called through the word at
  0x8C004008.
- It prints "dc-load console support enabled" and exits through DCLOAD_EXIT.
- The SCIF stays free. The serial probes drive it themselves, so they cannot run on a KOS whose console is the SCIF.

Without dcload the probes would still run, but on KOS's other path, with a 115200-baud console (about 16.6k Icyc per
character) sharing the SCIF.

**What it is.** 96 bytes loaded at 0x0C004000, dcload-ip's own place, which is zero in syscalls.bin:
- the re-entry at 0x8C004000 (the dcload start state's PR);
- the magic and the syscall entry;
- WRITE to fd 1 / 2 sends the bytes to the sim-control putchar port; EXIT writes the exit register; every other
  syscall returns -1. ASSIGNWRKMEM's -1 makes KOS take dcload_type = IP, as with dcload-ip.

With `--dcload`, the program is entered with board.md 5.2's measured dcload column (P2 entry 0xAC010000). soc_tb's
boot-failure check follows that start state's VBR (0x8C00F400).

**Its cache footprint (fixed during M5).** On the first unmodified cachetest run, "F WT store miss: no allocate (V)"
read 1 against the console's 0: a functional row, flagged by the probe itself.
- The cause is not the chip. The probe's X is in OC entry 0, and so is 0x8C004008. KOS's `dcloadsyscall` stub loads
  that word through P1 on every print, so after the probe's prints the stand-in's line (tag 0x0C004000) was valid in
  entry 0.
- On the console, dcload-ip's network code leaves entry 0 invalid. The same program's array rows read tag
  0x01848000 there, a Broadband Adapter buffer line, with V = 0.
- The stand-in now purges (OCBP) that line on every return. The rerun
  (`agents/verify/M5/probes2/cachetest`) reads V = 0, and cachetest's functional rows are all equal (99 / 99).

**Tests.**
- `dc_board_test` group `dcload` (on the ISS): the layout; every syscall's result; EXIT; a return to the re-entry.
  Planted bug `dcload` (the magic missing) is caught.
- `soc_tb --selftest dcload` (every build, in `v1-soc`): the stand-in through the chip, called as KOS calls it, with
  KOS's CCR. On the real-memory builds OC entry 0 must be invalid after a syscall. Plants `nodcload` (no image; im and
  rm) and `dcloadnopurge` (its OCBP replaced by a NOP; rm) are caught.
- The gate's `m5/check.py --kos` on every probe: the KOS banner, the "dc-load console support enabled" line, the exit
  line and exit code 0. `--self` rejects 7 perturbations per run.

## 5. Findings

**A. ci on the TRANSLATE = 0 build (fixed: ci runs on rmx).**
- On rm, ci made 64 board warnings, where M3's graft made none. ci's `utlb_rd` / `utlb_wr` rows switch the MMU on with
  an empty TLB, and on rm those accesses reach the board instead of faulting.
- On rmx, the complete chip, it gives 0 warnings and 15,863 exceptions (rm: 12,981). Its `mmu` rows are then compared
  (`--translate 1`: 784 tokens against rm's 727), and it passes with the 4 documented cold IRQ records.
- The gate runs ci on rmx and every other probe on rm, as M3's level-cache checks do: KOS never enables the MMU.

**B. The stand-in's cache footprint** (fixed; section 2).

**C. SOC.md 9.29, open (filed): CPU-visible board timing on the chip.** The board probes' `--timing` rows, which the
stand-alone model could not check, mostly pass: KOS init 390 ms, and the access costs. Two groups do not.
- **(a) boardio's GD step readings.** DRQ is seen at 414-437 against the console's 363-364, and every later reading
  moves with it. A bus trace of the same loop (`agents/scratch/M5/gdloop/`) shows why:
  - boardio's t0 is a PMCTR read right after three posted G1 writes. The chip takes it with one write on the bus and
    one in the one-entry WTB (freed when the BSC accepts the write), so its first status poll starts 74 Icyc after t0
    and its readings fall on a 296 / 414 grid.
  - The console's 363 needs its first poll to start about 28 Icyc after t0: nothing pending at t0.
  - The chip's posting matches the console for RAM (bsc-memmap `wr_nd` T8 74 = 74) and nearly for SB (84 against 86).
  - So either the console posts G1 writes one deep, or Holly holds the G1 write cycle longer. The board's GD write
    waits (7 Bcyc) and drive delays were fitted by `dc_board_test gdloop`'s replay, which assumed the former.
- **(b) boardregs' SQ -> VRAM32 / AICA RAM `+drain` / `+fifo` split.** 44 / 106 and 14 / 3360 against 97 / 53 and
  857 / 2542. The sums (150, 3374) equal the console's (150, 3399), and the issue times match: the board's Holly FIFO
  accepts the last bursts sooner and drains longer than the console's RDY# throttling. bsc-memmap's class
  `timing-board` rows show the same, and were never compared on the chip before: `pvr_pal wr_nd` T8 84 against 146.
- **Owners:** WI-BSC (the posting depth) and WI-BOARD (the Holly RDY / FIFO split, the GD delays).
- **The probe that settles it:** k posted G1 / SB / RAM writes, then a PMCTR read, for k = 1..4, and the same with an
  uncached read. Then refit the board's constants against the chip rather than a replay.
- **In the gate:** these rows are reported by a pattern (`V1_SOC_M5_B929`): 7 in boardio in the gate run (8 in
  batch 1, one GD reading landing inside its window this time) and 4 in boardregs. Every other `--timing` row gates.

**D. SOC.md 9.23, new evidence (open): interrupt acceptance during an IC miss.** The unmodified excint2's S PI
repetitions whose probe line is IC-cold are accepted *later* on the console and *earlier* on the chip.
- Console run 2: k = 21 / 19 / 20 / 20 / 19 / 17, against a warm 15-18.
- Chip: k = 4-7; at n = 5 both repetitions give 5 / 5, against the console's 19 / 19. Fewer ADDs retire before the
  take while the fetch waits for the fill.
- C1 rte's cold handler path gives k 4 against the console's 7.
- ci's cold IRQ records land 6-16 bytes past the console's.
- The rows are documented (KOS_DOC). Settling it needs 9.23's fetch-count probe of a cold branch target and a cold
  exception entry.

**E. S PH now matches the console exactly.** The unmodified excint2 prints S PH `7/7 0/7 8/8 0/7 8/8 7/7 0/0 0/0 6/6
7/7 7/8 6/6`, the console's line, including the cold 0 / 6 values earlier milestones classed as port artefacts.

**F. boardregs' AICA_RTC_LO post value (checker rule fixed).** The chip's run (191M Icyc) reads the seconds counter
before its first tick, 0x0C2D, against the console's 0x0C2E.
- Whether a second boundary falls between the pre and post dumps depends on the RTC's phase at the program's start,
  which the console does not fix; the board starts a second at time 0.
- `tb/bm/board/check.py` now accepts the console's value or one less for `post`; `pre` stays exact.
- A post of 0C2C or 0C2F, and a changed pre, are rejected; the model (0C2E) still passes.
