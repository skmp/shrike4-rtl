## 2. Findings and fixes

Each fix is in the unit's file, with a regression test in the unit's bench, and the unit's tests re-run.

### F1 (WI-DMAC, missing mechanism) -- the DTR never came from the data bus

Phase 1 delivered the DTR through the testbench port `ddt_tl`; the pins were driven but D63:0 was never sampled.
Fix: `v1_dmac_ddt` input `ddt_d` (D63:0), `d_s` captured at TR#, `d = ddt_tl.dtr_v ? ddt_tl.dtr : d_s`;
`v1_dmac.ddt_d` and `v1_soc` `.ddt_d(xb_rdata)`. Bench: `v1_dmac_tb` "cover DTR on the data bus" (a DTR driven on the
bus with TR# two Bclk after BAVL# loads CHCR0 / DMATCR0 / DAR0; TR# at 1..4 Bclk gives R D D D) and the old scan test
keeps an SZ-111 DTR on the bus; planted bug `V1_DMAC_BUG_25` (caught, 5 FAIL lines). SoC mutants `ddt_dbus` and
`soc_ddt_d` (ddtx never ends). Reruns: `make v1-dmac`, `v1-dmac-bugs`, `v1-dmac-int`, `v1-dmac-lint` PASS.

### F2 (WI-BSC, against [HW dmac1 S13, dmac2 T5]) -- the CPU starved behind a paced single-address DMAC stream

dmac1 S13 on the console polls ISTNRM all through a 64 KB CH2-DMA (first poll back during the transfer, ISTNRM 19 at
23,613 Icyc). On the chip the CPU's first poll returned after the end: `v1_bsc_arb` gave the DMAC every accept (DMAC >
CPU), and single-address units' accepts overlap, so the bus never went free for the CPU's MPX read. Fix: the CPU's turn
-- `v1_dmac_xfer.bus_rel` (the engine in REL, or idle with nothing to commit) -> `v1_dmac.bus_rel` -> `v1_bsc.dma_rel`
-> `v1_bsc_arb` `cpu_turn`: a CPU access that waits while the DMAC holds no bus session gets the next accept, before a
DMAC request raised after it; a burst session never releases; a lock is never broken. (A first version that granted
the turn only at a grant point failed the new bench group; relaxed to any DMAC release.) Effects: cycle steal gives
one CPU transaction per break (dmac2 T5: strict alternation, 2,001 / 2,000 units per 2,000 reads), S13's 64 KB with
the CPU polling through it ends at 23,722 Icyc against 23,613. The bare-metal T5 moved from 71.0 / 70.0 to 70.3 / 68.7
Icyc per pair (console 66.4 / 64.6; still M3's open row 9.25). Bench: `v1_bsc_tb` group `turn` (released: the CPU's SB
read accepted after 4 of 12 DMAC units; burst: after 12 of 12), `tb/v1_bsc_tb.sv` / `v1_bsc_agree_tb.sv` port wiring;
`v1_bsc_mutants.py` +2 (M6), 59 / 59 caught. SoC mutants `bsc_turn` (`V1_BSC_BUG_TURN`: ddtx row S, one poll in 64 KB)
and `dmac_norel`. Reruns: `make v1-bsc` (incl. agree), `v1-bsc-mutants`, `v1-bsc-lint` PASS. Errata: bsc-memmap.md,
dmac.md, SOC.md 3.3.2.

### F3 (WI-DMAC, data corruption) -- a single-address write's data took the next unit's byte enables

dmac1 under KOS had 2 DDT time-outs (maple response units at Icyc 139,992,838 / 140,392,872, during S11's channel-1
word-unit cycle steal; PCs 8C01B848 `perf_cntr_count`, 8C010AA4 `run1`). The VCD (`agents/scratch/M6/vcd/`,
`vcdpick.py`) showed channel 0's 32-byte maple response written with be ff / 30 / 30 / 30: the engine finishes a
single-address unit at its BSC accept, so the BSC's data pulls came while it already ran channel 1's word unit, and
`bwd.wd_be` came from the engine's current context. The board saw 14 bytes and never ended the unit. Fix:
`v1_dmac_xfer`'s single-cycle FIFO `sgl_q` carries each cycle's {lanes, TS, channel, write}; a single write's pulls
take `wd_be` from the FIFO head. Bench: the `v1_dmac_tb` BSC stub checks every single write's byte enables against its
own unit; test "cover single write lanes"; planted bug `V1_DMAC_BUG_26` (caught, 49 FAIL lines). ddtx row Y (Holly ->
memory units against channel-1 word units). SoC mutant `dmac_sgl_be`. Reruns: `make v1-dmac`, `v1-dmac-bugs`,
`v1-dmac-int`, `v1-dmac-int-bugs`, `v1-dmac-bm`, `v1-dmac-lint` PASS. SOC.md 3.3.3.

### Board phase-2 calibration (WI-BOARD files, M6's own new code)

- The engines ended (MDST 0, ISTNRM) before their last DTR was served: KOS's dmac1 S9 (iii) / (iv) wait for MDST 0 and
  then make an address error, which drops DDT requests (hm 14.3.6), so a queued response unit was lost ("maple:
  unknown response 0 on device C0"). Fix: PVR / G2 / maple end at their last DTR's `issued` callback (maple: `end_wait`
  for the last response DTR). Plant `maplerword` (`dc_board_test`).
- CH2-DMA pacing: with the board keeping channel 2's request line busy the DMAC's level-sense burst had no breaks.
  Holly's input FIFO modelled (`dc_sb.h`: 32 units, drained one per 11.70 Icyc), fitted to dmac1 S13's three
  transfers [P] (SOC.md 9.30 (b)).
- Maple reply words 6,628 Icyc apart ([HW] dmac1 S1's DEVINFO steps 52,916 / 53,128 Icyc).

## 7. Open items (SOC.md 9.30) and decisions for the lead

- 9.30 (a) Holly's unit timing: the console's first PVR-DMA unit lands ~276 Icyc after PDST (the board: < 90); the
  chip shows DMATCR0 = 1 in 4-9 of ~140 ddtprobe samples per DMA where the console shows none -- the chip's
  DTR-to-count-update window for Holly's units is longer than the console's [P]. End times within 0.2 %.
- 9.30 (b) CH2-DMA's start pattern: the FIFO pacing fits the 64 KB transfer (5 %); for the 32- / 64-unit transfers the
  chip's first poll returns after the end (83 Icyc), the console's during it (271 / 683): Holly's request pattern at
  a transfer's start (SB_C2DPRYC / C2DMAXL are 0 under KOS) is not pinned -- bounded above only.
- 9.30 (c) a DTR the chip drops (AE / NMIF, hm 14.3.6): the board gives the unit up after 400,000 Icyc [P]; the
  console's Holly likely hangs; the M6 checkers fail any run with a time-out.
- 9.30 (d) not exercised: GD-DMA (the no-disc drive never starts one: B5), sort-DMA (not modelled), PVR-DMA texture
  -> RAM timing on the console.
- 9.25 remains open (M3): the single-unit latencies and cycle steal with the CPU polling; T5 closer with the CPU turn
  but still 5-6 % slow (hm Table 13.16's pipelined transitions not modelled).
- Decision: phase 1 stays the default board; should later milestones (and M4 / M5's hello runs) move to `--ddt`?
  hello2f passes both ways.
