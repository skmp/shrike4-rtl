## 2. excint2's Holly IRL rows (`tb/bm/exceptions-intc`, WI-EXC's files)

**Why they could not pass.** The console ran excint2 under KOS, which routes vblank-in and the maple DMA end to
Holly level 2 (`IML2NRM 0x1008`), and some DMA ends to level 4. Its handler acknowledged those events as soon as they
arrived. The bare-metal port had neither: IML2/4/6 were 0, so the four `irl` probes waited 6-8M iterations for nothing.
This is why excint2 alone took 96M Icyc and 27 min at M1a. The expected file marked the five rows `board`, with no rule.

**Changes.**
- `crt0.S` sets KOS's routing as the console's "I holly" line printed it: IML2NRM 0x1008, IML4NRM 0x7C000, IML4ERR
  0x3000, level 6 none. It then acknowledges everything pending, as KOS's `asic_init` does.
- `shim/kos.h`: `irq_disable` / `irq_restore` stand in for KOS's handler. At the edges of every probe window they
  acknowledge the pending routed events, so an event that arrives inside a window stays pending, as on the console.
- **The acknowledge is branch-free**, writing 0 bits where nothing is pending. The first version tested `if (p)`, and
  the compare left SR.T set in the SR the C code hands 8 probes (`slot_ldcsr`, `fd_*`). Those rows failed on
  `r1=...f1`; the ISS showed the same, and the branch-free version fixed it.
- The other probes are unaffected: every one of them runs at IMASK 5 or above, where levels 2 / 4 are never accepted.
- **Rules** (`mkexpected.py`; `expected.json` changed in these five rows only; `check.py --board` checks them):
  - "I holly": the IML routing exact. ISTNRM / ISTEXT / ISTERR may hold any value: they are the board's SPG events at
    the print (vblank-out and hblank-in are routed nowhere), which KOS had acknowledged on the console.
  - The irl rows are `match` records with INT kept, SSR at the probe's IMASK, and SPC equal to the DT or the BF of the
    wait loop. The console shows both: L+2 once, L+0 twice.
  - Seven new PERTURB lines must be rejected: a level taken with another level's code, level 6 accepted at IMASK 6,
    level 2 at IMASK 2, a take outside the loop, the maple bit missing from IML2.

**Result on im** (level soc, `--board`, lockstep pass):

```
I holly: ISTNRM 00000030 ISTEXT 00000000 ISTERR 00000000 IML2 00001008/00000000/00000000 IML4 0007c000/00000000/00003000 ...
irl2_imask1  #0 EXP=180 INT=3a0 ... spc=L+0 ssr=40000010 ...
irl2_imask2  none ...
irl4_imask3  #0 EXP=180 INT=360 ... spc=L+0 ssr=40000030 ...
irl6_imask5  #0 EXP=180 INT=320 ... spc=L+0 ssr=40000050 ...
```

- excint, excint2 and excint3 together: 141 / 141 lines. excint2 now takes 33.3M Icyc instead of 96.2M.
- On rm at level cache, excint fails the same 12 rows as at M3-fix: C1 ldc_sr / rte / ipr_write, C4 ×8 and D cost.
  Their values moved slightly with the run-time's code layout (C1 k 7 vs 8, C4 busy 1061-1070 vs 1055-1065, D trapa 36
  vs 59). These are port-layout cold rows, SOC.md 9.28. excint3 passes.

**A directed check of the pins themselves** (`soc_tb --selftest hollyirl`; full board, render delay 3000 Icyc):
- PVR STARTRENDER raises render-done bits 2 / 1 / 0, routed to levels 6 / 4 / 2, all pending under IMASK 6.
- Lowering IMASK to 5, 3, 2 and 1 takes 0x320, then 0x360, then nothing, then 0x3A0.
- The handler acknowledges each level's bit and returns with IMASK 15.
- It passes on all four builds. Planted bug `V1_SOC_MUT_IRL_ORDER` (the pins reversed into `v1_intc`: levels 4 and 2
  swap, 6 does not) is caught.

## 3. timers-clock test K (tck, rm, lockstep)

`tb/bm/timers-clock/tck` is test K of the console's `tc.c`, split off at M1b because it needs the board's AICA RTC,
which advances every 199,505,792 Icyc (G9).
- It waits for an RTC second's edge, spins 2 × 199.5M PMCTR cycles, and waits for the next edge. Over the window it
  counts CPU cycles (PMCTR1) and TMU1 Pφ/4 counts.
- The check (`check.py --board --progs tck`, timers-clock 8.3) takes the ratio only. The absolute rate is the board
  model's.

```
K AICA RTC 1543310382 -> 1543310384 (2 s): 399011402 CPU cycles (199505701 per s), 24938212 TMU1 P/4 counts (12469106 per s), cycles/count 16.0000
console:   ... (3 s): 598517376 CPU cycles (199505792 per s), 37407336 TMU1 P/4 counts (12469112 per s), cycles/count 16.0000
```

- The run took 598,526,344 Icyc and 255.5M instructions. All 459.5M records passed in lockstep, including 51.4M
  VOLRD, mostly PMCTR and AICA RTC reads.
- It spanned 2 RTC seconds where the console's spanned 3: the rule asks for at least 2.
- The window is 182 Icyc short of 2 × 199,505,792 (91 per second): each edge is found by a polling loop that reads
  the RTC across the G2 bus. The ratio is exact.
- The run takes about 2 h at 70-130k Icyc/s, which sets the gate's length.

## 4. A WDT manual reset and a WDT power-on reset through the boot stub (`tb/bm/soc-adv/m4/wdtrst`)

**Testbench.** `soc_tb --resets N` lets N resets that the core did not request (WDT, H-UDI, an associative-write
multiple hit) re-boot the chip instead of ending the run:
- The chip restarts at 0xA0000000 and the boot stub runs again. The stub skips its power-on-only SDRAM entries unless
  EXPEVT = 0.
- The first such reset still ends the lockstep with the verdict "reset" (SOC.md 6.2).
- The summary lists every reset with its cycle, and the N + 1st ends the run as before.
- The `wdtreset` selftest and the `noreset` plant are unchanged.

**The program.** It uses the m1b run-time, with its state in P2 memory, which the manual reset's continuing refresh
keeps:
- **Boot 1** gives every register the boot stub does not rewrite a distinctive value and reads them back. That covers
  SCIF (a loopback overrun: SCLSR2.ORER = 1), SCI (SCSPTR1's I/O bits), RTC (CIE / AIE, PES, the alarms' ENB, the
  counters), UBC (both channels armed on addresses nothing touches), CCN, INTC, TMU, DMAC, MMU, PMC and STBCR2. Then
  the WDT overflows with RSTS = 1 (manual).
- **Boot 2** reads and stops the WDT first, since TME is held and it would fire again. It clears the stub's MSTP0 / 1
  and reports every register next to its set value. It then repeats the set-up and fires a WDT power-on reset.
- **Boot 3** reports again.

`m4/check.py` holds SOC.md 2.3's manual and WDT-POR columns; the program does not judge itself.

**Result.**
- rm: resets at Icyc 141,386 (manual) and 387,146 (power-on), 600,313 Icyc in all. All 102 rows pass. The SDRAM
  monitor is clean across both resets (1,541 commands, 174 refreshes).
- im gives the same result.
- `--self`: all 103 perturbations are rejected.
- The rows as SOC.md 2.3 states them:
  - **WTCSR** reads E7 → F7 after the manual reset and C7 → D7 after the power-on reset: the WDT's own reset keeps the
    register and sets WOVF.
  - **SCIF** is initialised: ORER cleared, SCFSR2 0x60.
  - **SCI** is initialised: SCSPTR1's I/O bits are 0 although a module stop would have kept them.
  - **RTC**: CIE / AIE / PES are cleared, RTCEN / START and the alarm values kept, and ENB is cleared by the power-on
    reset only.
  - **UBC**: all ten registers held on manual, 0 on power-on.
  - **EXPEVT** reads 020 / 000; TRA and INTEVT are held, then 0.
  - **ICR** is 0x8000, the IPRs and TMU are initialised, and CHCR is 0.
  - **Held on manual, 0 on power-on**: SAR / DAR / DMATCR, PTEH / TEA, PMCR2, STBCR2.
  - **0 on both**: MMUCR, PTEL / TTB / PTEA.
- **Planted bugs** (sed mutants of the units, `make v1-soc-mutants`), all caught:
  - `wdt_wovf_own`: WOVF cleared by the WDT's own reset.
  - `scif_man_held`, `sci_man_held`: the SCIF / SCI not initialised by a manual reset.
  - `ubc_man_clear`: the UBC cleared by a manual reset.
  - `rtc_man_keep`: RCR1 / RCR2 not cleared by a manual reset.
- `V1_SOC_MUT_CHECK` runs soc-adv/m4 programs with `--resets 2 --no-uart-check`, without `--ccr`, and accepts the
  lockstep verdict "reset".

## 5. Sleep fast-forward: not delivered (SOC.md 7.4, G8)

The computed task listed "sleep fast-forward". SOC.md 7.4 (binding) and critic resolution G8 make it optional and not
a phase-1 deliverable: "Phase 1 simulates every cycle while the core sleeps".

An exact fast-forward would need every counting unit to accept a warp: the TMU, WDT, RTC, the CPG divider, the BSC
refresh, the SCIF baud generator and the DMAC. None of the M4 gate items sleeps for long; hello0 does not sleep at
all before its exit stub. So `soc_tb` still simulates every cycle.

`v1_tmu.next_evt` is in place for a later timewarp mode. KOS's idle thread in hello1 (M5) is where it would first
pay off: thd_sleep(100) is about 20M Icyc.
